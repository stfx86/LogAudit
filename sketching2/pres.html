🔍 ANALYSE PRÉLIMINAIRE — QUESTIONS DES ENQUÊTEURS
QUESTION 01
Pourquoi unrar s'exécute-t-il avec uid=0 (root) ? Le processus webapp ne devrait jamais avoir de privilèges root pour décompresser un fichier utilisateur.
QUESTION 02
Pourquoi le fichier uploadé s'appelle backup_data.rar ? Un utilisateur légitime uploadant une archive dans une webapp ZipVault ne devrait pas nommer son fichier ainsi.
QUESTION 03
Quel est le contenu exact de l'archive ? L'argument -o+ (overwrite) combiné à -ep (ignore paths) dans la commande unrar est inhabituel.
CONSTAT INITIAL
Corrélation des logs : 1h après l'upload, une connexion SSH réussie depuis la même IP 105.68.208.123 est enregistrée sur le serveur. Ce n'est pas une coïncidence.
HYPOTHÈSE DE TRAVAIL
L'archive backup_data.rar contenait un fichier malveillant avec un chemin path traversal pointant vers /root/.ssh/authorized_keys. La version non patchée de unrar a exécuté cette écriture en root → accès SSH direct.
PLAN D'INVESTIGATION
Suivre la chaîne : Upload → SSH Session → Reconnaissance → Exfiltration → Privesc → Backdoor → Cause Racine (unrar non patché)

⚡ Mécanisme d'Exploitation

L'archive RAR malveillante contient une entrée avec un chemin relatif malformé :

# Contenu de backup_data.rar :
wkkyblef ← fichier leurre
../../../../root/.ssh/authorized_keys
# ^^^^^ PATH TRAVERSAL
 
# unrar < 6.1.7 ne valide pas le chemin
# → écrit la clé SSH dans /root/.ssh/
# → exécuté en root par webapp
 
# unrar ≥ 6.1.7 : bloque la traversée
# → "Security violation in path: ../"

Le serveur ubuntu-target utilisait unrar 6.1.1 installé depuis les dépôts Ubuntu 22.04 non mis à jour. Le patch était disponible depuis 6 mois au moment de l'attaque.

✅ Mesures Correctives
  • 🔧apt upgrade unrar → mettre à jour vers ≥ 6.1.7 immédiatement
  • 🚫Ne jamais exécuter le processus webapp en tant que root — utiliser un compte dédié sans privilèges
  • 🛡️Activer les mises à jour automatiques de sécurité (unattended-upgrades)
  • 📁Valider et sanitiser les chemins de toutes les archives avant extraction
  • 🔒Corriger le fichier sudoers : supprimer NOPASSWD:ALL
  • 🔑Ne jamais stocker de credentials en clair dans le code source — utiliser des variables d'environnement
  • 🔍Surveiller les accès à /root/.ssh/authorized_keys avec Wazuh FIM en temps réel
💡
LEÇON FONDAMENTALE
Une seule mise à jour manquante — unrar 6.1.1 → 6.1.7 — a permis à l'attaquant de déposer une clé SSH root sans aucune authentification, déclenchant une chaîne de compromission complète en moins de 2 heures. Le patch existait depuis 6 mois. La gestion des correctifs est une ligne de défense critique, non optionnelle.
